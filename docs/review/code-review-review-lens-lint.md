## 运行时验证与新发现的阻断项

修完上表的 🔴 之后在真实 Chrome 里加载扩展复测（`agent-browser --extension review-lens open <gitlab MR>`），**同一条错误依旧出现**：

```
[review-lens] 启动失败： TypeError: Failed to fetch dynamically imported module:
chrome-extension://8365d194-dbf7-4e32-9450-9dfe50448fde/content/entry.js
```

说明语法错误只是其中一个障碍，还有第二个独立的阻断项：

| 级别              | 文件:行号                          | 违反的约定                                             | 现状                                                                                                                                                                                                                                                                                                     | 处置                               |
| ----------------- | ---------------------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| 🔴 阻断（已修复） | `review-lens/manifest.json` WAR 段 | 资源的暴露方式必须与消费方式一致：模块要以模块方式加载 | `web_accessible_resources` 带 `"use_dynamic_url": true`，资源只能通过每 session 轮换的 GUID URL 访问。GUID URL 能被 `fetch` 取到（200、`text/javascript`），但 **无法作为 ES 模块加载**，于是 `bootstrap.js` 的 `import(chrome.runtime.getURL("content/entry.js"))` 必然失败——插件在任何站点上都挂不起来 | 已移除 `use_dynamic_url`。取舍见下 |

定位过程（每一步都在真实 Chrome 上跑）：

1. 逐个 `fetch` entry.js 及其模块图里全部 16 个资源 —— 全部 200，MIME 是 `text/javascript`，排除「资源没进 `web_accessible_resources`」与 MIME 不符。
2. 在 node 里真实 `import()` 整张模块图 —— `content/entry.js` 与 `ui/drawer.js` 都成功并导出预期符号，排除 linking 错误与顶层抛错。
3. 在无 CSP 的 `example.com` 上从页面上下文 `import()` GUID URL —— 同样失败，排除宿主页 CSP（GitLab 的 `script-src` 确实是 `strict-dynamic` + nonce，一度是最像的嫌疑）。
4. 换成静态 URL（`chrome-extension://<扩展 ID>/content/entry.js`）`import()` —— **成功，导出 `init`**。差异只在 `use_dynamic_url`，根因锁定。
5. 移除该字段后重新加载扩展、重开同一 MR 页 —— `[review-lens] 启动失败` 日志消失；另在页面里手动 `import("ui/drawer.js")` 并驱动 `createDrawer`，宿主节点建起、loading 与 failed 两态都渲染正常、`close()` 能移除节点。

**取舍要知道**：`use_dynamic_url` 的用途是防止页面用固定 URL 探测「这个扩展装没装」。去掉之后任意页面都能探测到本扩展。这里没有第三条路——扩展的资源必须以 ES 模块方式加载，而动态 URL 不支持模块加载。想缩小暴露面只能收窄 `matches`，但用户可以自行注册任意 GitLab 站点，manifest 里穷举不了，所以 `http://*/*`、`https://*/*` 得保留。

**顺带说明一处没有改的地方**：`bootstrap.js` 的 `isOrphaned` 只认 `Extension context invalidated` 与 `message port closed`，这次的 `Failed to fetch dynamically imported module` 不被当成孤儿、会打进 `console.error`。看起来是噪声（扩展重载后旧 content script 也会报同一条），但正是它让这个 bug 暴露出来。把这条 message 加进孤儿判定会把真实的模块加载失败一起静默掉，因此保持现状。

## 不采信的机器结论

`custom/comment-style` 报的 16 处里有 4 处没有采信，理由是规则的判据是「注释后面紧跟的第一个 token 属不属于 export 声明」，它没有「文件级说明注释」这个概念：

- `core/gitlab.js:1`、`core/register-origin.js:1`、`core/thread.js:3`、`ui/code-pane.js:3` 四处都是文件顶部的模块说明（讲这个文件是什么、鉴权走什么策略、三个视觉通道怎么分工），与下面第一个 `export` 之间只隔一个空行，于是被判成「导出声明的注释必须用 `/** */`」。它们讲的不是那个导出，改成 JSDoc 会让编辑器把模块说明当成该常量的文档提示，反而更误导。
- 若希望机器信号干净（CI 里零报错），可行的做法是把文件级说明与首个导出之间插入一行别的代码，或把说明搬到 README/架构文档里。这属于取舍，不作为违规。

另有 2 处「多段应合并」的判定改按错位记（已列入上表）：`core/thread.js:9` 与 `ui/drawer.js:74` 的两段注释各有自己的目标，合并会把两件事糊成一段。

## 未能确认的项

- **抽屉的完整业务流程没有端到端验证。** gitlab.com 未登录时 `discussions` 接口返回 401，取不到代码评论，因此「入口按钮挂上 → 打开抽屉 → 左右两栏对照」这条主链路只在组件级验证过（`createDrawer` 能建节点、渲染 loading 与 failed、能关闭）。带登录态的内网 MR 页需要你自己回归一次，重点看入口是否出现、抽屉三态是否正常。
- `bootstrap.js` 的挂载队列已改完并在真实页上验证过路由切换（见上表），但**验证是在未登录的 gitlab.com 上做的**：那里取不到 discussions，`init()` 会走到 `loadError` 分支。「取数成功后切走再切回」这条路径（要真的执行 `detach()` 与 `drawer.close()`）没跑到，需要带登录态的实例回归。
- `unregisterOrigin` 没有像 `registerOriginScripts` 那样校验 origin 格式，传一个非法 origin 进去会直接调 `chrome.*`。实际调用方只会传列表里已校验过的 origin，且真实 `chrome.permissions.remove` 会抛错并被聚合成 `{ ok: false }`，所以没有改；如果以后有别的调用方，这里要补一次校验。

## 复现方式

扩展目录保持零依赖，lint 从外部仓库跑，不在本仓库留任何文件：

```bash
# frontend-code-spec 需要 Node >= 22.12（仓库 .nvmrc 为 22.22.2）
cd ~/Desktop/frontend-code-spec && pnpm install

# 在 browser-plugin 下临时写一份 config，跑完删除
cat > /tmp/review.eslint.config.mjs <<'EOF'
import customConfigs from "/Users/lyndon./Desktop/frontend-code-spec/eslint/index.js";
export default [...customConfigs];
EOF
cd ~/Desktop/browser-plugin
~/Desktop/frontend-code-spec/node_modules/.bin/eslint \
  --no-config-lookup --config /tmp/review.eslint.config.mjs "review-lens/**/*.js"
~/Desktop/frontend-code-spec/node_modules/.bin/stylelint \
  --config ~/Desktop/frontend-code-spec/.stylelintrc.js "review-lens/**/*.css"

# 语法兜底：每个文件单独解析一次
for f in review-lens/**/*.js; do cp "$f" /tmp/chk.mjs; node --check /tmp/chk.mjs || echo "FAIL: $f"; done
```

本轮修复实际用的方式：注释形态 13 处**手工改**（没跑 `eslint --fix`，它会把那 4 处不采信的文件级说明注释一并改成 JSDoc）；样式声明次序用一份只启用 `recess-order` 的临时配置 `--fix`，避开另外 12 处不在条款内的规则，改完核对过两个 CSS 文件的声明集合与修前完全一致、只有顺序变了，随后用 `prettier --write` 复位 `drawer.css` 的格式。
