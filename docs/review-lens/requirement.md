# 需求文档

## 1. 产品概要

**一句话愿景**：在 GitLab MR 的讨论页上，把「评论指的是哪行代码」和「后来改成了什么样」并排摊在同一个抽屉里，让人通过读别人的代码评审来学习。

**交付形态**：Web/前端 — Chrome Manifest V3 扩展，content script 在 GitLab MR 页面内注入侧边抽屉。

> 交付形态驱动下游：接触面设计归属（前端→视觉设计阶段 / 服务·命令·库→架构阶段的接触面契约）、验收方式与留证形态。完整映射见 SKILL §2.4。

| ------------------------------ | ------------------------------------------------------------------------------ | ------------------ |

## 5. 功能边界

### 5.1 做（纳入实现的功能）

- MR 讨论页每条代码评论旁注入解读入口，唤起页面内右侧抽屉
- 抽屉展示评论来源信息与评论时版本的代码片段，锚点行高亮
- 抽屉展示该主题下的全部评论与回复（讨论往返的结论常在回复里）
- 评论时版本 ↔ 修正后版本并排对比，滚动同步、差异高亮，区分「已改动」与「至今未改动」
- 评论正文标识符与代码位置的关联：高亮、跳转、候选相关行、展开完整方法体
- 学习卡片：存储、弹窗内浏览筛选删除、导出 Markdown
- 站点适配：运行时识别 GitLab（内网与 gitlab.com 同一套实现）、中英文 UI 兼容
- 鉴权：优先复用页面登录态，不可用时降级为用户配置 token
- 容错：取数失败给出可区分原因与重试

### 5.2 不做（排除在产品之外，非延后）

- AI 解读评审意图与 Java 语法 — 原因：内网代码发往第三方模型有合规风险，需先落定公司内网 AI 网关；本轮明确不做（Q-3）
- GitHub PR 支持 — 原因：另一套 DOM 与 API，工作量翻倍且当前场景在内网 GitLab（Q-1）
- 任何写操作（回复评论、resolve 主题、提交 suggestion） — 原因：本产品定位为阅读理解工具，避免在内网评审上误操作
- MR 概览区的非代码评论 — 原因：没有代码锚点，不是本产品要解决的痛点
- 卡片云端同步与团队共享 — 原因：单机学习工具，本地存储足够
- 自建后端服务 — 原因：所有数据来自 GitLab 自身接口，无服务端可省则省

## 6. 非功能要求

| 类别   | 要求                                                                                                                                    |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| 性能   | 入口注入不阻塞宿主页首屏；点击入口到抽屉内容渲染完成 ≤ 1s（同一评论重复打开走缓存 ≤ 200ms）；不为未点击的评论预取数据                    |
| 兼容性 | Chrome MV3；GitLab 中英文界面；目标站点为携程内网 GitLab 与 gitlab.com（具体 GitLab 版本待确认，见 §7 Q-8）                              |
| 安全   | 代码内容不出浏览器，不向任何第三方发送；token（若需要）仅存 `chrome.storage.local`，不出现在日志与导出物中；仅在识别为 GitLab 的页面注入 |
| 可用性 | 失败态可区分且可重试；抽屉不遮挡评论主体交互，可关闭；沿用宿主页视觉语言，不与 GitLab 界面互斥                                            |
